# Prototyp: sprachliche Entwicklungsaufträge

`codex_voice/development_orders.py` ist ein lokales Prozessmodell für Issue-gebundene Entwicklungsaufträge. Es importiert keine GitHub-, Shell-, SSH-, Modell- oder Deployment-Clients. Eingaben sind bereits strukturierte Felder; es gibt keinen Transkriptions- oder Intent-Parser.

Die Auftragsreferenz muss auf ein Issue im Control-Repository `lizard4king/SmartHome` zeigen. Zielprojekte sind `SmartHome` oder das ausdrücklich gewählte HA-Add-on `lizard4king/smarthome-spotify-addon-ha`. Das endgültige Add-on-Ziel folgt aus PR #52, der nachgewiesenen Installation und dem aktuellen `fresh`-Remote. Der Legacy-Slug `lizard4king/smarthome-spotify-addon` ist kein zulässiges Ausführungsziel. `RepositoryCatalog` verlangt weiterhin eine explizite Auswahl und hat keinen Standardwert.

Stand 18.10.2026: Dieses lokale Integrationspaket baut auf Add-on-PR #61 (Commit `0db95d1`) auf und übernimmt ausschließlich das Auftragsmodell, seine Tests und diese Dokumentation aus dem lokalen Prototyp vom 11.10.2026. Es verbindet das Modell weder mit `app.py`, Docker, einer API noch einem Executor. Es installiert keinen Dienst und erweitert keine Server-, GitHub- oder Geräteberechtigung. Die Abnahmekriterien der SmartHome-Issues #59 und #60 bleiben offen; diese Integration ist keine Ende-zu-Ende-Abnahme.

Jeder Auftrag verlangt Issue, Zielprojekt, Zieltext, eine ASCII-Request-ID (1–128 Zeichen aus Buchstaben, Ziffern, Punkt, Unterstrich, Doppelpunkt und Bindestrich) und einen bereits verifizierten Sprecher-Schlüssel mit 64 kleingeschriebenen Hexzeichen. Die zugelassene Sprecherliste wird beim Erzeugen des OrderBooks zwingend übergeben. Das Modell ordnet niemals Alexa-Konto, Gerät oder Namen einer Person zu. Gleiche Sprecher-ID plus Request-ID und gleichem Inhalt liefert denselben nicht-terminalen Auftrag; abweichender Inhalt oder ein terminaler Auftrag unter derselben Request-ID wird abgewiesen.

Ein Plan schaltet nur auf `awaiting_execution_approval`. Danach muss der verifizierte Einreicher jeden Freigabeschritt ausdrücklich bestätigen; das Modell bietet keine Vier-Augen-Freigabe. Auch eine noch nicht gestartete EXECUTE-/Push-/Merge-/Deploy-Freigabe kann widerrufen werden; ein aktiver Remote-Vorgang kann als fehlgeschlagen protokolliert werden. Ausführung, Tests und Review müssen anschließend protokolliert werden. Push, Merge und Deployment haben jeweils getrennte „gestartet“-Zustände. Branch-Namen werden ausschließlich als `codex/<opaque-order-id>` gebildet. Status und Fehlercode sind abfragbar. Abbruch ist nur vor Start der ersten Ausführung möglich; danach können Freigaben widerrufen, aber Ergebnisse nicht als abgebrochen maskiert werden.

## Noch nicht integriert

Nach beendeter Ausführung kann der Einreicher einen ruhenden Auftrag mit `close_without_further_action` ohne weiteren Push/Merge/Deploy terminal auf `CLOSED` setzen. `closed_after_stage` erhält den vorherigen Meilenstein; Ergebnisse und Freigaben bleiben erhalten. Das bedeutet keine Rücknahme vorhandener Änderungen oder Remote-Artefakte. Aktive Aktionen lassen sich damit nicht als beendet maskieren. Die ursprüngliche Request-ID bleibt auch nach Abschluss gesperrt, damit eine verspätete Wiederholung keinen zweiten Auftrag erzeugt. Die ausdrücklich begrenzten Prozesslaufzeit-Kontingente werden durch diesen Abschluss nicht freigegeben; für den dauerhaften Dienst fehlen noch persistente Status-/Deduplizierungsdaten und deren begrenzte Aufbewahrung. Widerrufene Freigaben sind im Prototyp kein unveränderliches Auditprotokoll.

Das OrderBook ist flüchtig und lebt nur im Prozessspeicher. Es nimmt höchstens 1000 Aufträge je Prozesslauf und 100 je Sprecher an; abgeschlossene, fehlgeschlagene und abgebrochene Aufträge zählen bis zum Prozessneustart mit. Es ist nicht an `app.py`, `VoiceJobs`, Skill-Intents, die SmartHome-Repository-Auswahl, GitHub API, Codex CLI, Filesystem-Sandbox oder Serverbetrieb angeschlossen. Lese- und Fortschrittsoperationen verlangen im Prototyp einen zugelassenen Sprecher und prüfen die Auftragszugehörigkeit; daraus entsteht noch keine vertrauenswürdige echte Identität. Die 64-stelligen Personenschlüssel müssen später ausschließlich von einer vertrauenswürdigen Identitäts- und Allowlist-Grenze kommen. Textfilter erlauben ZWNJ/ZWJ für sprachliche Schriftsysteme, lehnen andere Format-Steuerzeichen sowie Variation Selectors ab. Plan-/Test-/Review-Einträge sind noch nicht signiert oder mit externen Belegen verknüpft.

Die spätere Integration sollte als separater Entwicklungsdienst auf dem Smart-Home-Server laufen. Er muss pro Auftrag einen isolierten Checkout und Branch erzeugen, bestehende Änderungen schützen, Ressourcen/Zeit begrenzen und nur lesbare Tests plus Diff-/Review-Berichte liefern. Allgemeiner Lumi-Kontext, Erinnerung und Notion-Inhalte dürfen keine Shell- oder Schreibberechtigung erteilen. Push, Merge und Deployment bleiben getrennte, ausdrücklich genehmigte Aktionen. Keine Docker-Socket- oder Hostvollrechte aus dem Voice-Prozess.

Für den End-to-End-Auftrag muss ein Offline-/Fake-Test den Weg vom strukturierten Auftrag bis zum geprüften lokalen Diff abbilden, bevor eine echte Repository-Berechtigung auf dem Server eingerichtet wird.
